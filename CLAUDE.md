# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install       # install dependencies
npm run dev       # start Vite dev server
npm run build     # production build to dist/ (also used by CI/deploy)
npm run preview   # preview the production build locally
```

There is no test suite and no linter configured in this repo.

## Architecture

Hugo's Kitchen Notebook is a 100% static recipe app: Vite + React + Tailwind, no backend, no build-time API calls, no database. Recipes are just Markdown files, and use metric units only (g/kg/ml/l/cm/°C plus tsp/tbsp) by convention.

**Recipe pipeline** (the core of the app):
1. Recipes live as `.md` files in [`_recipes/`](_recipes/) with YAML-ish frontmatter (title, prepTime, portions, tags, description, plus optional `title_nl`/`title_fr`/`title_de` and `description_nl`/`description_fr`/`description_de`) followed by a base `## Ingredients` + `## Preparation`, and optional per-language `## Ingredients (nl)` / `## Preparation (fr)` / etc. sections.
2. [`src/lib/frontmatter.js`](src/lib/frontmatter.js) hand-rolls a minimal frontmatter parser (strings/numbers/booleans/flow-lists/block-lists) — deliberately not a full YAML parser, to avoid Node/Buffer polyfills in the browser bundle. It parses arbitrary flat keys generically, so the `_nl`/`_fr`/`_de` suffixed keys needed nothing added here.
3. [`src/lib/recipes.js`](src/lib/recipes.js) uses `import.meta.glob('/_recipes/*.md', { query: '?raw', import: 'default', eager: true })` so Vite statically inlines every recipe file at build time — this is what makes the whole app buildable as a static site with zero server code. Adding a recipe is just dropping a new `.md` file in `_recipes/`; there is no registry to update. `parseSections` groups body sections by an optional `(xx)` language suffix on the `## Heading` line (e.g. `## Ingredients (nl)` → name `ingredients`, lang `nl`); `loadRecipes` builds each recipe's base fields plus a `translations` map (`{ nl?, fr?, de? }`, only populated when that language actually has content). `localizeRecipe(recipe, locale)` returns the recipe with title/description/ingredients/steps swapped for a locale's translation, falling back to the base fields when that locale/recipe has none — components call this at render time, keyed off the current UI locale. `slugify`/routing always uses the base title, never a translation.
4. [`src/lib/scaleText.js`](src/lib/scaleText.js) detects quantities in ingredient text (mixed numbers, fractions, unicode vulgar fractions, decimals, ranges like "2-3") and scales them by a portion ratio, formatting back to the nearest "nice" fraction glyph where possible — locale-independent, since numbers/ranges are written identically across languages by convention (only the surrounding words change).
5. [`src/lib/safetyFlags.js`](src/lib/safetyFlags.js) flags specific ingredients (aubergine, mushroom, ricotta, feta, olive) by regex so they're visually highlighted — matches on whatever language is currently displayed, so coverage is incomplete for translated ingredient text beyond words that happen to be shared loanwords across en/nl/fr/de; this list is meant to be edited per-user preference, not treated as fixed logic.

**Routing**: `HashRouter` (see [`src/App.jsx`](src/App.jsx)) is used deliberately — `/#/recipe/...` URLs work on GitHub Pages without any 404-redirect workaround.

**Dev-only LLM recipe editor**: the chat-with-local-LLM UI lives in [`src/components/EditorPanel.jsx`](src/components/EditorPanel.jsx) (recipe list + chat + raw draft/save, extracted so one implementation can be mounted two ways) — either full-page at `/editor` ([`src/pages/Editor.jsx`](src/pages/Editor.jsx), just the page header + `<EditorPanel />`), or as a floating overlay available on every page via [`src/components/ChatDrawer.jsx`](src/components/ChatDrawer.jsx) (`<EditorPanel compact />`, mounted once in `App.jsx` sibling to `<Routes>` so it persists across navigation — lets you keep looking at a recipe while chatting instead of navigating away). Both the `/editor` route and `ChatDrawer` are registered behind `import.meta.env.DEV` so Rollup tree-shakes all of it out of the production build entirely — verified by grepping `dist/` for editor-only strings after a build. The LLM (Ollama, LM Studio, or any OpenAI-compatible `/chat/completions` server — configured via `llm.config.json`, gitignored, see `llm.config.example.json`) is reached through [`vite-plugins/recipeEditorApi.js`](vite-plugins/recipeEditorApi.js), a Vite plugin registered only via `configureServer` (dev-server-only hook, never runs during `vite build` or `vite preview`) that exposes `/api/recipes` (GET/POST/DELETE, reads/writes `_recipes/*.md` directly) and `/api/llm/chat`.

The chat proxy does real OpenAI-style tool-calling, not just text passthrough, through a small registry (`TOOL_REGISTRY` in the plugin) mapping a tool name to `{ schema, execute(args) }` — `execute` always returns `{ ok, resultText, extra? }`. The client's request body includes a `tools: ['save_recipe']`-style array of names it wants enabled for that conversation; the plugin looks up the matching schemas, and when the model calls one, dispatches to `execute`, feeds `resultText` back as a `role: 'tool'` message, and does a follow-up completion to get the model's natural-language confirmation before replying (any `extra` fields — e.g. `{ saved: {...} }` — are merged into the JSON response). This is what lets the user just say "save it" mid-conversation instead of manually clicking "Insert reply into draft" → "Save recipe" (that manual two-button path still exists as a fallback). Failed tool calls loop back to the model for up to 3 attempts before giving up. Filename resolution (`resolveFilename` in the plugin) mirrors the client-side `deriveFilename` in `EditorPanel.jsx` — both slugify the frontmatter `title:` line the same way, so a chat-saved and button-saved recipe end up named identically.

Three tools are registered: `save_recipe` (writes a recipe file, used by `EditorPanel.jsx`), `update_fridge_items` (overwrites `fridge.json`'s item list, used by `Fridge.jsx`), and `update_recipe_tags` (rewrites just the `tags:` frontmatter line of one existing recipe, used by the "Auto-tag all recipes" button — `EditorPanel.jsx`'s `autoTagAll` loops over every recipe sequentially, one `/api/llm/chat` call each with [`src/lib/autoTagPrompt.js`](src/lib/autoTagPrompt.js) as the system prompt and that recipe's full raw content as context). Adding a fourth tool means: define its schema + `execute` in `TOOL_REGISTRY`, and pass its name in the client's `tools` array.

The exact markdown shape the LLM must produce — now including the `_nl`/`_fr`/`_de` frontmatter keys and the eight `##` sections (base + 3 translations, for both Ingredients and Preparation) — is defined in [`src/lib/recipeFormatPrompt.js`](src/lib/recipeFormatPrompt.js); keep it in sync with `frontmatter.js`/`recipes.js` parsing rules if those change.

Hugo's standing personal preferences (portion-size defaults, step-detail expectations) are **live-editable, not just a source file**: `GET`/`POST /api/preferences` (same plugin) read/write `preferences.json` (gitignored), seeded from `DEFAULT_PREFERENCES_TEXT` in the plugin the first time it's requested. [`src/lib/recipePreferences.js`](src/lib/recipePreferences.js)'s `RECIPE_PREFERENCES` export is now only the client's initial-render/offline fallback (shown before the `/api/preferences` fetch resolves) — keep its text in sync with the plugin's `DEFAULT_PREFERENCES_TEXT` seed, since they're meant to match. `EditorPanel.jsx` fetches the live text on mount into `preferencesText`, concatenates it with `RECIPE_FORMAT_SYSTEM_PROMPT` via a `useMemo`'d `systemPrompt`, and exposes a gear-icon modal (`showPreferences`/`preferencesDraft`) to view/edit/save it — this is "memory management" from the UI, no code editing required for a preference change.

`llm.config.json` has two fields specifically for hybrid-reasoning models (Qwen3.5-style, i.e. models that think-by-default): `reasoningEffort` (sent as `reasoning_effort` on the OpenAI-compat path) and `nativeOllama` (bool). When `nativeOllama: true`, `callLlm` in the plugin targets Ollama's **native** `/api/chat` instead of `${baseUrl}/chat/completions`, sending `think: false` instead of `reasoning_effort` — this exists because Ollama's OpenAI-compat endpoint silently drops both params once `tools` are present (every request here sends tools), causing multi-minute hangs or empty `content` on a reasoning model. Native mode also returns `tool_calls[].function.arguments` pre-parsed as an object rather than a JSON string; `parseToolArguments()` normalizes both shapes — keep it even if you revert to a non-reasoning model, since it's a harmless no-op there.

The recipe draft panel renders a **live preview** by default, not raw markdown — `parseRecipeMarkdown(draft)` (exported from `recipes.js`, factored out of `loadRecipes` so it can run over in-progress textarea content, not just files on disk) parses the current draft into the same shape as a real recipe, `localizeRecipe` swaps in whichever of its `translations` the user picks via language tabs (only shown when the draft actually has more than the base language), and `RecipePreview` renders it exactly like the real recipe page (title/description/tags/ingredients/steps) instead of showing `---`/`##` markdown soup. An "Edit raw markdown" toggle still exposes the underlying textarea for manual edits/paste — that's the only place raw markdown is intentionally shown.

`validateRecipeMarkdown` in the plugin runs before every write (manual POST and tool-called save alike) and exists because small local models occasionally emit content that looks right but silently breaks parsing — seen in practice: a missing closing `---` (frontmatter.js then treats the entire file as unparsed body, so title/tags/portions vanish with no error) and `tag:` instead of `tags:`. Those are hard `errors` that block the write. Missing NL/FR/DE frontmatter keys or sections are `warnings` instead — they never block a save (the app just falls back to the base language for that field), but on the tool-call path they're appended to the "Saved as X.md" tool-result message so the model can see what's missing and offer to fill it in. A hard-error failure is fed back to the model as a `role: 'tool'` error message so it can retry, capped at 3 attempts before falling back to a message pointing the user at the manual draft box.

**Fridge**: [`src/pages/Fridge.jsx`](src/pages/Fridge.jsx) (route `/fridge`, dev-only same as `/editor`) is a small pantry tracker — a chat (using the `update_fridge_items` tool and [`src/lib/fridgeAssistantPrompt.js`](src/lib/fridgeAssistantPrompt.js) as its system prompt) lets the user say what they have/used, in any of the four languages, and the model normalizes it to short English ingredient names in `fridge.json` (gitignored, read/written via `/api/fridge` GET/POST in the same plugin). The "What can I cook?" button doesn't use a tool at all — it just sends a user message with the current fridge items plus a compact `title: ingredients` summary of every recipe (built client-side from the already-imported `recipes` array) and asks the model to rank matches conversationally; matching is base-English-only (doesn't consider `translations`), which is fine since it's just for the model's own reasoning, not rendered.

**Fridge inbox** (async, away-from-home path into the same fridge): unlike `fridge.json`, [`_fridge/inbox.md`](_fridge/inbox.md) is a **tracked** file, specifically so a note jotted through github.com's web editor (e.g. from a phone, no `npm run dev`/Ollama needed) reaches whichever machine later runs the app. It has two headings, `## Nieuw` (freeform notes go here) and `## Verwerkt` (a dated archive). `GET`/`POST /api/fridge/inbox` (same plugin, registered *before* the `/api/fridge` middleware since connect matches by path prefix and the more specific mount must win) read the current `## Nieuw` text and, on POST, move it into a new dated entry at the top of `## Verwerkt` and clear `## Nieuw` — `splitFridgeInboxSections`/`archiveFridgeInbox` in the plugin do the parsing. `Fridge.jsx` fetches the inbox on load; if non-empty it shows a banner with a "Verwerken" button that feeds the raw text through the *same* `send()`/`update_fridge_items` chat path manual typing already uses, then archives on success. Archiving never deletes — a misread note just stays visible in `## Verwerkt` instead of silently vanishing. Committing/pushing `_fridge/inbox.md` afterward is a manual step (no auto-git from the dev server), same as how `_recipes/*.md` changes are handled.

**i18n**: both UI chrome and recipe content (title/description/ingredients/steps, when a recipe provides that language — see the recipe pipeline section above) are translatable across English/Dutch/French/German via a small hand-rolled layer — no i18next, consistent with this repo's general avoidance of dependencies for small surface areas. [`src/lib/translations.js`](src/lib/translations.js) holds the UI-chrome dictionaries + `translate(locale, key, params)` (supports `{placeholder}` interpolation and a `_one`/`_other` plural suffix keyed off `params.count`); recipe-content translation is separate, handled by `localizeRecipe` in `recipes.js`. [`src/hooks/useLocale.jsx`](src/hooks/useLocale.jsx) provides `LocaleProvider`/`useTranslation()` via React Context — Context (not a per-component hook like `useDarkMode`) is required here because changing the language must re-render every consumer at once, not just the component that owns the toggle. A first-time visitor (no saved `kitchen-notebook-locale`) defaults to `'nl'` — this is a Dutch grocery app first — regardless of browser language; the `LanguageSwitcher.jsx` `<select>` dropdown can still pick any of the four, and that choice persists. Language names in the dropdown are always shown untranslated in their own language (English/Nederlands/Français/Deutsch) so a user can find their language regardless of the current locale. Tags themselves are never translated — they stay a single shared list of English kebab-case identifiers used for matching/filtering/URLs in every language — but their *display* is: `translateTag(tag, locale)` (also in `translations.js`, a small per-tag `TAG_LABELS` map) is what `RecipeCard.jsx`/`RecipeView.jsx`/`TagFilter.jsx` render instead of the raw slug, falling back to the English slug for any tag not yet in the map (e.g. a brand new recipe's tag). `Fridge.jsx` is fully wired into this system too (via `fridge*`-prefixed keys) — earlier it was English-only regardless of the site's locale.

**Theme default**: [`src/hooks/useDarkMode.js`](src/hooks/useDarkMode.js) defaults a first-time visitor (no saved `kitchen-notebook-theme`) to **light** mode unconditionally — it used to fall back to the OS/browser's `prefers-color-scheme`, which meant a dark-mode OS made the site default to dark for every new visitor regardless of intent. `DarkModeToggle.jsx` is unchanged; a saved preference (once toggled) still always wins.

**Deals & pricing** (`/deals`, `/shopping-list`, and the price badges on `/recipe/:slug`): the backend pipeline that produces `public/data/*.json` is documented in [`backend/README.md`](backend/README.md) — see that file for scraping details (19-store registry, vision-LLM vs. structured connectors, `--essentials`, product images). On the frontend:
- [`src/hooks/useDeals.js`](src/hooks/useDeals.js) merges the per-store flyer JSON *and* `data/essentials.json` (everyday staples' current prices, scraped regardless of whether they're on sale — see backend's `--essentials`) into one flat, searchable/filterable deal list on `/deals`; essentials-sourced entries are tagged `dealType: 'basisprijs'` and can surface stores `index.json` doesn't otherwise know about (zero flyer coverage but a live price for some staple).
- Every ingredient match in `ingredient-matches.json` is already sorted cheapest-first with a `winkel` per match, so "top 3 alternatives" and "cheapest across only the stores I'm visiting" are both pure frontend features, no backend change needed. [`src/lib/ingredientCost.js`](src/lib/ingredientCost.js)'s `pickBestMatch(matches, storeScope)` picks the cheapest match within an optional store scope (falling back to the overall cheapest, flagged `inScope: false`, if none of the scoped stores carry that ingredient); `estimateRecipeCost` uses it and also returns a per-store `byStore` breakdown. [`src/hooks/usePreferredStores.js`](src/hooks/usePreferredStores.js) (localStorage, same pattern as `usePantryStaples`) persists "which shops I'm actually visiting" across the whole app — set on `/shopping-list` (chip picker above the per-store grouping, which already existed and just needed to respect a scope), it also applies to each recipe's cost line and turns the ingredient price badge into a `<details>` disclosure revealing the next two cheapest alternatives.

**Deployment**: [`.github/workflows/update-and-deploy.yml`](.github/workflows/update-and-deploy.yml) scrapes deal data (see backend/README.md), then builds with `npm ci && npm run build` and publishes `dist/` via `actions/upload-pages-artifact` + `actions/deploy-pages`. Two things must be kept in sync for Pages to work:
- `REPO_NAME` (the Vite `base` path) in [`vite.config.js`](vite.config.js) must match the actual GitHub repo name (e.g. `/recipe-app/`), or `/` for a `<user>.github.io` repo.
- The repo's **Settings → Pages → Build and deployment → Source** must be set to **GitHub Actions** (this is a one-time manual step in the GitHub UI, not something the workflow file can set).
